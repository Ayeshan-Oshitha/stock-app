# Repository: Monorepo

## Decision

**One Git repository (monorepo) for the backend and the frontend.**

## Why

1. **Solo developer now.** One repo to clone, build and keep current.
2. **Features cut across services.** For example, "undo sell" touches portfolio, gateway and web; in a monorepo that is one commit.
3. **Shared contracts in one place.** Event and API contracts never go out of sync; TypeScript types can be generated from the backend's OpenAPI.
4. **One command runs everything** with Docker Compose.
5. **Easy to split later.** Strict service boundaries mean any service folder can become its own repo.

Large companies such as Google, Meta and Microsoft (Windows) use monorepos, but with custom tooling. At this project's size, plain Git and GitHub are enough.

## Folder structure

```
stock-app/
├── src/
│   ├── gateway/                  # API Gateway (.NET + YARP)
│   ├── services/
│   │   ├── portfolio/            # Portfolios, holdings, lots, sells, undo, dividends (.NET)
│   │   ├── market-data/          # CSE ingestion, prices, corporate actions (.NET)
│   │   ├── analytics/            # Indicators, risk, forecasting (Python)
│   │   └── knowledge/            # Report PDFs, extraction, RAG (Python)
│   ├── shared/
│   │   ├── dotnet/               # Small shared .NET libraries (logging, auth, messaging)
│   │   └── contracts/            # Event & API contracts shared by all services
│   └── web/                      # React + Tailwind frontend
├── deploy/
│   ├── docker-compose.yml        # Run everything locally / on the VM
│   ├── docker-compose.dev.yml
│   ├── keycloak/                 # Keycloak realm config (login, users, roles)
│   └── env/                      # .env.example templates (no real secrets)
├── docs/                         # Architecture, decisions, commands, future work
├── scripts/                      # Setup, DB seed, data import scripts
├── .github/workflows/            # CI/CD (path-filtered per service)
├── .editorconfig                 # Code style for all languages
├── .gitattributes                # Line endings (LF for container files)
├── .gitignore                    # .NET, Python, Node, data, secrets
├── global.json                   # Pins the .NET SDK
├── Directory.Build.props         # Shared .NET build settings
├── Directory.Packages.props      # Central NuGet package versions
├── StockApp.slnx                 # .NET solution
├── CLAUDE.md
└── README.md
```

## Per-language configuration

| Purpose | .NET | Python | React |
|---|---|---|---|
| Runtime version | `global.json` | `.python-version` (root) | `.nvmrc` + `engines` |
| Project settings | `Directory.Build.props` | `pyproject.toml` per service | `package.json`, `tsconfig.json` |
| Package versions | `Directory.Packages.props` | `pyproject.toml` | `package.json` |
| Lock file | optional | `uv.lock` per service | `package-lock.json` |
| Quality | analyzers, nullable, warnings as errors | Ruff (`ruff.toml` at root), mypy | strict TypeScript, ESLint, Prettier |

Python and React configuration files are created when those parts are set up.

## What never goes into Git

| Item | Where it goes |
|---|---|
| Secrets (`.env`, keys) | Local `.env` files (only `.env.example` is committed) |
| PDFs, CSV price data | `data/` (ignored) or object storage |
| Trained models, experiments | Object storage / MLflow |
| Build output, `node_modules`, `.venv` | Regenerated by tools |

## Rules

- Services may only share code through `src/shared/` (infrastructure helpers and contracts). **No business logic in shared code.**
- One root `.gitignore` and `.gitattributes`. Tool-generated nested ones are merged into the root.
- CI uses path filters so only changed services build.

## If the team grows

| Stage | Approach |
|---|---|
| Solo | Monorepo |
| Small team (2–10) | Monorepo + CODEOWNERS + path-based CI |
| Several teams | Monorepo with Nx/Bazel and a platform team, **or** split into domain repos (e.g. portfolio, market-data, intelligence, web, platform) with contracts published as versioned packages |
